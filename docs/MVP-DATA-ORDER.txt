================================================================
  HECO PORTAL — INITIAL DATA-ENTRY ORDER (Clean DB → Operational)
  Companion to MVP-BOOTSTRAP-FLOW.txt
  Written: 2026-05-14
================================================================

This file answers ONE question:

  "Starting from a completely clean database, in what order must
   I add data and users so that everything works?"

Each step depends on every step above it. Skipping or reordering
silently breaks something downstream. Read pitfalls at the bottom.

----------------------------------------------------------------
  THE 15 STEPS — IN STRICT DEPENDENCY ORDER
----------------------------------------------------------------

----------------------------------------------------------------
STEP 1.  HCT ADMIN USER
----------------------------------------------------------------
  WHY FIRST
    Nothing else can be entered through the UI until at least one
    user with user_role='hct_admin' exists to log in.

  HOW
    Seeder:   php artisan db:seed --class=AdminUserSeeder
              creates admin@hecoapp.com / password (hct_admin) +
              collaborator@hecoapp.com / password (hct_collaborator)

    Then in UI:
      hecoadmin.test/login → Admin tab → HCT Users
        - add the real Admin and Collaborator accounts
        - delete the seeded test accounts when no longer needed

  TABLES TOUCHED
    users (user_role = 'hct_admin' / 'hct_collaborator')

  VERIFY
    php artisan tinker --execute="echo App\Models\User::where('user_role','hct_admin')->count();"


----------------------------------------------------------------
STEP 2.  SYSTEM LISTS  (master dropdowns)
----------------------------------------------------------------
  WHY HERE
    Every entity below picks values from these lists:
      - Experiences pick experience_type
      - SPs pick services_offered / accommodation_category /
        vehicle_type / activity_type
      - Payments pick payment_mode
    Without these, dropdowns are empty and saves fail validation.

  HOW
    Seeder:   php artisan db:seed --class=SystemListSeeder

    Then in UI:
      Control Panel → System Lists tab
        - review each list type, add/rename/deactivate

  LIST TYPES SEEDED
    service_type, accommodation_category, vehicle_type,
    activity_type, experience_type, payment_mode

  TABLES TOUCHED
    system_lists (list_type, name, sort_order, is_active)


----------------------------------------------------------------
STEP 3.  TRAVEL PREFERENCE LISTS  (pricing-critical)
----------------------------------------------------------------
  WHY HERE
    The pricing engine (CostCalculatorService::getMultiplierMap())
    matches stored trip column strings against the EXACT labels in
    these lists. If a label is missing, the multiplier silently
    falls back to 1.0 — meaning prices are wrong but nothing errors.

  HOW
    Seeder:   php artisan db:seed --class=PreferenceListsSeeder

    Then in UI:
      /travel-preferences  →  view + edit each of the 5 list types

  LIST TYPES SEEDED
    accommodation_comfort, vehicle_comfort, guide_preference,
    travel_pace, budget_sensitivity

  ⚠ STRICT RULE
    DO NOT rename a label here without updating
    CostCalculatorService::getMultiplierMap() in code. Doing so
    silently breaks pricing.


----------------------------------------------------------------
STEP 4.  SETTINGS  (GST, margins, base costs)
----------------------------------------------------------------
  WHY HERE
    CostCalculatorService reads these at trip-build time. Trips
    created before settings exist would have margin/GST = 0 baked in.

  HOW
    Seeder:   php artisan db:seed --class=SettingSeeder
              seeds gst_percent=5, default RP/HRP/HCT margins,
              base transport/accommodation/guide per-day costs,
              site_name, site_email, AI defaults.

    Then in UI:
      Control Panel → Settings tab → override defaults to match
      your real business rules.

  KEY KEYS
    gst_percent, default_rp_margin_percent,
    default_hrp_margin_percent, default_hct_commission_percent,
    base_transport_per_day, base_accommodation_per_night,
    base_guide_per_day, site_name, site_email


----------------------------------------------------------------
STEP 5.  CURRENCIES
----------------------------------------------------------------
  WHY HERE
    Homepage currency switcher + traveller-facing price display
    fail soft if currencies are missing (defaults to INR raw).

  HOW
    Seeder:   php artisan db:seed --class=CurrencySeeder
              seeds USD/EUR/GBP/INR/AED/AUD/CAD/JPY/SGD with
              rate_to_usd values.

    Then in UI:
      /currencies  →  edit rate_to_usd periodically, add new ones.

  TABLES TOUCHED
    currencies (code, symbol, name, locale, flag, rate_to_usd)


----------------------------------------------------------------
STEP 6.  REGIONS  (foundation entity)
----------------------------------------------------------------
  WHY HERE
    Every downstream entity is FK'd to a region:
      - service_providers.region_id
      - experiences.region_id
      - regenerative_projects.region_id
      - trip_regions.region_id
    Without active regions, you can't create SPs, Experiences,
    or RPs. Without anchor_points/lat/lng, the map and AI flow
    are degraded.

  HOW
    Seeder:   php artisan db:seed --class=RegionSeeder
              20 regions across Asia/Africa/Europe/Oceania/SA
              with anchor_points + lat/lng + descriptions.

    Then in UI:
      /regions  →  for each region you'll OPERATE in:
        - confirm anchor_points (Chandigarh, Bhuntar, etc.)
        - confirm latitude/longitude (used by the homepage map)
        - set external_url → matching page on himalayanecotourism.com
          (MVP §19 SEO continuity)
        - is_active = false for regions you're not yet serving

  TABLES TOUCHED
    regions


----------------------------------------------------------------
STEP 7.  AI PROMPTS
----------------------------------------------------------------
  WHY HERE
    The chat handler reads ai_prompts at every request. Without
    them, the AI falls back to a generic system prompt and:
      - ignores the HECO conversation flow
      - hallucinates experiences not in the catalog
      - emits invalid RECOMMEND_IDS / ADD_TO_TRIP tags

  HOW
    Seeder:   php artisan db:seed --class=AiPromptSeeder
              seeds traveller_chat + others.

    Then in UI:
      Control Panel → AI Prompts tab → tune system_prompt /
      user_prompt_template. Save & test via chat.

  KEYS SEEDED
    traveller_chat, itinerary_generator, (others)


----------------------------------------------------------------
STEP 8.  PDF TEMPLATES
----------------------------------------------------------------
  WHY HERE
    Trip Manager → Generate PDF reads pdf_templates for header,
    footer, CSS, paper size, orientation. Without at least one
    template (key='itinerary_pdf'), PDF generation fails.

  HOW
    UI only:
      Control Panel → PDF Templates tab → Add Template
        - key: itinerary_pdf
        - name, paper_size, orientation, header_html, footer_html,
          css

  TABLES TOUCHED
    pdf_templates


----------------------------------------------------------------

  After steps 1-8, every admin page should render with empty

    /dashboard, /leads, /trips, /providers, /provider-applications,

  Every one must be HTTP 200, no Whoops, empty tables.

----------------------------------------------------------------
STEP 9.  HRPs  (Heco Regional Partners — one per region)
----------------------------------------------------------------
  WHY BEFORE HLHs / OSPs
    An HRP is the regional coordinator. They take a margin on every
    trip in their region. The financial structure of trips assumes
    a region has an HRP. Easier to seed HRPs first, then HLHs/OSPs
    underneath them.

  HOW — Path A (SP self-application, preferred audit trail)
    1. SP visits hecoportal.test/join, fills form,
       provider_type=hrp, region=<their region>.
    2. SP receives SpApplicationReceivedEmail.
    3. HCT visits /provider-applications → Approve.
    4. System auto-creates linked users row (user_role='hrp')
       and emails set-password link via SpApplicationApprovedEmail.
    5. SP follows link → sets password → logs in.

  HOW — Path B (HCT enters directly, for known partners)
    1. /providers → Add Provider
    2. provider_type=hrp, status=approved, region_id=<id>
    3. Create user row manually (tinker or admin UI)
    4. Send credentials offline.

  REQUIREMENTS
    - One HRP per region (region rule)
    - email must be unique on service_providers (migration enforces)
    - status must be 'approved' for the SP to log in

  TABLES TOUCHED
    service_providers, users (one per SP)


----------------------------------------------------------------
STEP 10.  HLHs  (Heco Local Hosts)
----------------------------------------------------------------
  WHY HERE
    experiences.hlh_id is a required FK. You cannot create even
    one Experience until at least one HLH exists in the target
    region with status='approved'.

  HOW
    Same as Step 9, but provider_type=hlh.
    Set services_offered (Title Case labels from system_lists),
    accommodation_categories, vehicle_types (if they drive),
    activity_types.

  ⚠ STRICT RULE
    services_offered stores TITLE-CASE labels ("Transport",
    "Accommodation", "Meals"). Trip service_type columns store
    LOWERCASE singular ("transport"). The mapping happens in
    SpMatchingService::serviceOfferedLabel — don't bypass it.


----------------------------------------------------------------
STEP 11.  OSPs  (Other Service Providers — optional at boot)
----------------------------------------------------------------
  WHY HERE
    OSPs handle services OUTSIDE experiences — long-distance
    transport, external hotels, specialized guides. They're not
    needed for the platform to function; add when you have actual
    OSP partners to onboard.

  HOW
    Same as Step 9, provider_type=osp.
    Common services: transport (with vehicle_types) or activities
    (with activity_types).


----------------------------------------------------------------
STEP 12.  SP PRICING ROWS
----------------------------------------------------------------
  WHY HERE
    Each approved SP needs per-service rates. The pricing engine
    consults sp_pricing when an experience involves a specific SP.
    Without rates, calculations fall back to settings defaults.

  HOW
    /providers/<sp_id>/edit → SP Pricing section → Add Row
    Per-service-type fields:
      - Accommodation:  per category × per occupancy (single /
        double / triple) — e.g. "Cat C - Standard" × "double" = ₹1800
      - Transport:      per km × per vehicle type — e.g.
        "SUV (Innova/Crysta)" = ₹25/km
      - Guide:          per day — e.g. "English-speaking" = ₹3000/day
      - Activity:       per person / per group / per day

  TABLES TOUCHED
    sp_pricing


----------------------------------------------------------------
  ── STOP & TEST POINT 2 ──
  After steps 9-12, SP self-service should work end-to-end:
    - SP can log in (with the password they set)
    - /sp/dashboard loads with their role-specific section
    - /sp/profile/edit lets them update their data
    - SP can manually block dates on /sp/dashboard calendar
    - SP can save an iCal URL for inbound sync
  Test with the SP account you just approved.
----------------------------------------------------------------


----------------------------------------------------------------
STEP 13.  REGENERATIVE PROJECTS (RPs)
----------------------------------------------------------------
  WHY HERE
    Each region you operate in SHOULD have an active RP. If a
    region doesn't have one, set another region's RP as fallback
    via fallback_for_regions. Without either, the Your Impact tab
    on every trip in that region renders empty (broken promise of
    a regenerative-travel platform).

  HOW
    /regenerative-projects → Add Project
    Required fields:
      - name, region_id, action_type (reforestation /
        fire_prevention / ecological_restoration / education / etc.)
      - short_description (traveller-facing)
      - impact_unit (trees / hectares / kg_CO2)
      - cost_per_unit (₹ per impact unit — used in impact calc)
    Optional but recommended:
      - long_description, active_periods, paused_periods,
        fallback_for_regions, main_image, gallery

  REGION COVERAGE RULES
    For every region with at least one active Experience:
      EITHER the region has its own active RP
      OR     the region is listed in some other RP's
             fallback_for_regions

  TABLES TOUCHED
    regenerative_projects


----------------------------------------------------------------
STEP 14.  EXPERIENCES
----------------------------------------------------------------
  WHY HERE
    Hard FK requirements:
      - region_id     (Step 6)
      - hlh_id        (Step 10)
      - type          (Step 2 — from system_lists experience_type)
      - duration_type (less_than_day / single_day / multi_day)
      - short_description (NOT NULL)
    Validators enforce all of these — saves will 422 if missing.

  HOW
    /experiences → Add Experience
    Fill out:
      - Identification: region, HLH, type, duration
      - Descriptions: short (≤500 chars), long (unlimited)
      - Cost breakdown: cost_accommodation, cost_logistics,
        cost_guide, cost_activities, cost_other
        → base_cost_per_person auto-summed from these
      - Constraints: min/max group, difficulty, age, fitness
      - Seasonality: available_months[] / restricted_months[] /
        unavailable_months[]
      - Inclusions: includes_accommodation/_transport/_guide/
        _activities/_meals + accommodation_category
      - Day-wise details (for multi_day): per-day title +
        short_description + inclusions
      - Card image (year/month upload via ImageUploadService)
      - Gallery images (multiple)

  ⚠ POLICY
    Disable (is_active=false) rather than delete obsolete
    Experiences — they stay visible in historical trip records.

  TABLES TOUCHED
    experiences, experience_days


----------------------------------------------------------------
  ── STOP & TEST POINT 3 ──
  After step 14 the platform is content-ready:
    - Guest opens hecoportal.test/ → map shows operational regions
    - Filters return real experiences (region, type, difficulty)
    - Experience detail page renders day-wise info, photos, prices
    - AI chat grounds to real catalog (no hallucinated treks)
  Smoke-test as a guest before opening to real travellers.
----------------------------------------------------------------


----------------------------------------------------------------
STEP 15.  TRAVELLERS  (self-onboarded — no admin action)
----------------------------------------------------------------
  WHY LAST
    Travellers self-register via /sign-up. They appear in the
    system organically after launch — no admin entry needed.

  AUTOMATIC FLOWS
    - On first trip-building action:
        LeadService::createOrGetLead auto-creates a Lead row,
        stage='follow_up'.
    - On first payment received via Trip Manager:
        traveller status → Client,
        trip status → confirmed,
        lead stage → won.
    - On trip completion:
        Client status → Former Client.

  HCT VISIBILITY
    /travelers tab — lists travellers who have at least one
    confirmed trip.
    /leads tab — actionable follow-ups (Follow-up stage only).


================================================================
  THE THREE "SILENT KILLERS" — DO NOT SKIP THESE
================================================================

  ❌ Skip STEP 3 (Travel Preference Lists)
     → pricing multipliers silently fall to 1.0×. Trips price
     wrong, no error, no log. Customer pays less than they should,
     or way more.

  ❌ Skip STEP 7 (AI Prompts)
     → chat ignores HECO conversation flow, hallucinates non-
     existent experiences, emits invalid RECOMMEND_IDS. Traveller
     sees plausible-sounding but fictional Himalayan options.

  ❌ Skip STEP 13 (RPs or fallback)
     → Your Impact tab on every trip in that region renders
     nothing. Core "regenerative travel" promise broken silently.


================================================================
  QUICK BOOTSTRAP COMMAND (all seeders, in correct order)
================================================================

  # From a clean DB
  php artisan migrate:fresh
  php artisan db:seed --class=AdminUserSeeder        # Step 1
  php artisan db:seed --class=SystemListSeeder       # Step 2
  php artisan db:seed --class=PreferenceListsSeeder  # Step 3
  php artisan db:seed --class=SettingSeeder          # Step 4
  php artisan db:seed --class=CurrencySeeder         # Step 5
  php artisan db:seed --class=RegionSeeder           # Step 6
  php artisan db:seed --class=AiPromptSeeder         # Step 7
  # PDF Templates: UI only — Control Panel → PDF Templates
  # Steps 9-14: real business data, enter via UI
  # Step 15: traveller self-service

  # OR do all seeders at once (DatabaseSeeder enforces the order):
  php artisan migrate:fresh --seed

  # Then restart Herd to flush OPcache:
  "C:\Users\<you>\.config\herd\bin\herd.bat" restart
